## 動作

FastAPI起動時と、その後各バッチ終了から5分ごとに最大3施設を確認する。
施設本体・推薦候補を対象に、未試行を優先し、同じ期限なら公式出典登録済み・定番を優先する。
既存の公式サイト検証器がOSMの同一ID・名称・位置を照合して公式URLを探索し、
公式ページと案内ページから営業時間・休業日・料金を抽出する。
Geminiが公式ページの抽出結果と前回値を評価して、採用する項目・再取得・要確認を選択する。
再取得は1施設につき最大1回（Gemini判断は最大2回）。モデルは既存のGEMINI_MODEL設定を利用する。
出典に存在する項目だけ選択可能で、Geminiが生成した値・URL・日時は保存できない。
さらにサーバー側の明示的な保存ルールを適用し、モデルの判断だけでは保存を許可しない。

- 出典URL付きの具体的な項目と施設名を確認：保存、30日後に再確認。
- 根拠不足・取得失敗：以前の値と確認日時を維持。1時間から最大7日へ再試行間隔を延長。
- 前回保存値との差分・休業告知：自動上書きせず要確認。比較候補と出典を履歴に記録。
- 項目が今回見つからない：消さず、項目別の過去の確認日時を保持。
- Geminiのエラー・不正応答・キー未設定：保存しないで再試行。ルールのみの成功へ切り替えない。

履歴にはGeminiのモデル名、各判断の行動・理由・採用候補、判断に渡した観測結果を残す。
既存のルールのみで確認した履歴はそのまま残り、Gemini判断として表示しない。

確認とは公式ページの記載を読み取れた意味で、現在営業中との保証ではない。
要確認を承認する編集機能や、推薦への新しい公式情報の適用はこの段階では含まない。

## 保存・API

`backend/data/catalog_agent.sqlite3` に対象キュー、前回確認値、全試行の履歴を保存する。
元の施設JSON・推薦区分は変更しない。管理画面はJSONと保存値を結合したAPIを読む。
画面上の履歴は直近50件、DBには全履歴を保存。再起動しても期限と結果は維持する。

- GET `/api/catalog-agent`: 状態、直近履歴、根拠、差分、次回期限
- GET `/api/catalog-agent/catalog`: 施設一覧に公式確認結果を結合
- POST `/api/catalog-agent/run`: ローカル・同一Originから最大3件を確認

`CATALOG_AGENT_ENABLED=0` で自動実行を停止（再起動が必要）。手動実行は可能。
`CATALOG_AGENT_DB` でSQLite保存場所を指定できる。
ローカルではサーバー停止中は動かない。Cloud RunではFirestoreとScheduler経由のJobを使う。
初期設定・移行・デプロイは [クラウド運用手順](cloud-catalog-deployment.md) を参照。

URL取得は既存の公開IP固定・リダイレクト検査・応答サイズ制限・時間制限を利用する。
ページ内容はテキスト表示し、ページ内の指示やスクリプトは実行しない。
