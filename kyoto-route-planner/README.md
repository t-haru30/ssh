# ConcierGO

既存アプリとは独立して動く、全国の駅を起点に周辺観光地を提案する日帰り・宿泊ルートアプリです。利用者が出発駅、出発日・時刻、テーマ、立ち寄り件数を指定すると、駅周辺の候補スポットからルートを選び、駅すぱあとAPIで公共交通経路を検索します。「現在地から探す」は駅すぱあとAPIの周辺検索で半径5km以内の駅・バス停などを最大10件表示し、最寄りの候補を出発地に設定します。選択した周辺候補の位置を使って観光候補を検索します。`GET /api/routes/random` も選択中の出発地を起点にします。`GEMINI_API_KEY` を設定すると、ルートのスポット名とテーマをGemini APIへ送り、タイトルと短いストーリーを追加します。未設定時もルート検索自体は利用できます。Docker版はOpenStreetMap由来の候補のみを同梱します。P12を取り込む従来のデータベースはローカル試作用です。

WindowsでDockerを使って起動する場合は、[Windows向けDocker導入・起動手順](docs/docker-windows.md)を参照してください。WSLの導入から設定ファイルの作成、起動・停止までを順番に説明しています。

## 構成

旅程の編集・訪問記録・JSON保存・駅名検索は [日帰り旅程の操作](docs/day-trip-guide.md)、口コミ・公開情報のAI要約は [機能とサーバー設定](docs/recommendation-evidence.md)、Docker版のデータと設定は [公開用ランタイム](docs/public-runtime.md) を参照してください。

- `frontend/`: React、TypeScript、Vite、MapLibre GL JS
- `backend/`: FastAPI。同梱OSM候補またはYahoo! JAPAN APIによる施設検索、駅すぱあとAPIによる経路検索
- `Dockerfile`: フロントエンドとAPI、ビルド時に生成したOSM候補データを1つのコンテナにまとめる構成。

Yahoo! JAPAN APIと駅すぱあとAPIの認証情報はバックエンドだけで使い、ブラウザーには渡しません。`PLACE_SEARCH_PROVIDER=public_catalog` では同梱OSM施設候補を使い、Yahoo!モードではローカルサーチAPIを使います。通常のルート候補が不足する場合は、指定半径内の同梱候補で補います。取得元と不足状況は結果に表示します。現在地周辺の候補は駅すぱあとAPIの `/geo/station` を交通種別無指定・半径5kmで検索し、近い順に最大10件を返します。MapLibreの地図タイルはOpenFreeMapを使います。

### Yahoo!ローカルサーチAPI

Yahoo!モードで施設を検索する場合は、バックエンドの`.env`に次を設定してください。公開カタログモードでは不要です。

```env
YAHOO_APP_ID=取得したAppID
```

AppIDは[Yahoo!デベロッパーネットワーク](https://e.developer.yahoo.co.jp/)で取得してください。AppID未設定、通信エラー、不正応答、結果0件の場合はYahoo!由来の空結果と状態メッセージを返します。APIキーは`.env`へ保存し、Gitへコミットしないでください。

### スワイプ用の軽量アイデアAPI

`GET /api/ideas/random` はテーマに沿ってYahoo!から2〜3件のスポットを選び、タイトルと短いストーリーを返します。`theme`（`all`、`history`、`temple`、`nature`、`food`）と`spot_count`（2または3）は任意で指定できます。駅すぱあとAPIは呼び出しません。`GEMINI_API_KEY`が未設定またはGeminiを利用できない場合は、スポット名とテーマからローカルでタイトル・ストーリーを組み立てます。

```text
GET /api/ideas/random?theme=nature&spot_count=2
```

応答には`theme`、`title`、`story`、`places`、`image_url`、画像クレジット、`image_verified`、`image_place_id`、`copywriting_source`、`note`が含まれます。写真は先頭スポットの名称が完全一致し、Wikipedia記事の座標が500m以内で、著作者・出典・許諾を確認できる場合だけ返します。地図・ロゴ・人物画像などのメタデータも除外します。画面では検証フラグとスポットIDが一致する画像だけ表示します。旧データの未検証写真、画像未発見・通信失敗時は写真を表示しません。Gemini利用時は`copywriting_source`が`gemini`、フォールバック時は`fallback`です。

Geminiの既定モデルは`gemini-3.8-flash`です。別の利用可能なモデルを使う場合だけ、`backend/.env`で`GEMINI_MODEL`を明示的に指定してください。

Wikipediaの画像検索は追加キーなしで利用できます。カードのクレジットから著作者・元画像ページ・ライセンスを確認できます。

「見つける」の表示中カードは `POST /api/routes/photo` で先頭から最大3施設の実写真を探します。施設名の完全一致と500m以内の位置、画像ファイル名、著作者・出典・再利用条件を確認し、採用した写真の施設名とクレジットを表示します。一致する写真がなければ画像なしで表示し、AI生成画像やテーマ画像で補いません。カードをめくるたびに画像を生成する処理も停止しました。

共有の `GEMINI_API_KEY` がある場合は、取得済み写真の説明文が対象施設の撮影写真を示すか、AIで意味を照合します。AIは画像自体の目視確認やURL・ライセンスの決定を行いません。キーがない場合も、施設名と写真種別が説明から確認できる画像に限って利用できます。AI補助は同時1件・プロセスあたり20試行までで、成功した写真情報は6時間再利用します。詳しくは [施設写真の取得とAI補助](docs/real-place-photos.md) を参照してください。

Wikimedia APIがHTTP 403を返す場合、APIキー不足ではなく、Wikimediaのロボットポリシーまたは実行環境の送信ネットワークによる拒否の可能性があります。本アプリは連絡先情報を含むUser-Agent、`maxlag`、画像メタデータ要求の一括化、検索結果キャッシュで不要なアクセスを抑えます。それでも403が続く場合は、サーバーログのHTTPステータスと`server`ヘッダーを確認し、ネットワーク管理者にWikimedia APIへの許可設定を依頼してください。Wikimedia側の制限であれば、[ロボットポリシー](https://w.wiki/4wJS)を確認のうえ、必要な利用量について`bot-traffic@wikimedia.org`へ問い合わせてください。制限を迂回するための別プロキシやブラウザー経由取得は行いません。画像が取得できない間はカードのグラデーション背景を使用します。

Discoverのスワイプ画面では`frontend`フォルダーで `npm install framer-motion` を実行してから開発サーバーまたは本番ビルドを実行します。Search内のIdeaDeckは画面から非表示ですが、コンポーネントと`useSwipeDeck`の実装は残しています。

### 日帰り旅程の編集

「旅をつくる」の日帰り初回提案では、出発駅・帰着駅、使える時間、1人あたりの予算と、自然・文化・食事・カフェ・買い物の複数の好みを指定できます。事前登録した候補から、帰着までの徒歩換算時間と判明分の予算に収まる組み合わせを端末内で選びます。初回提案だけでは外部の施設・交通APIへ通信しません。遠い帰着駅など条件に合う候補がない場合は、入力を保持して条件の見直しを案内します。

食事1か所1,500円・カフェ1か所600円を変更可能な計画用見積もりとして使います。空欄は未確認です。施設料金や交通費が不明なら合計は未確認のままにし、実際の予算内を保証しません。各予定に登録ジャンル・テーマと選んだ好みから推薦理由を表示します。好みを変更しても選んだ行き先・固定予定は保持します。帰着地・好み・計画用見積もりも下書きに保存します。

「見つける」や保存済みプランの詳細から、選んだスポット・順序・地域・滞在目安を「旅をつくる」へ引き継げます。日帰り旅程では使える時間（30〜720分）と1人あたりの予算（0〜50,000円）を指定し、固定していない予定だけを調整できます。固定は行き先・滞在時間・指定した開始時刻を保持します。各予定の編集から滞在時間、固定開始時刻、施設・飲食費の見積もりを入力でき、追加・入れ替え・削除は変更案を確認して反映します。変更を取り消したり、ひとつ前の旅程へ戻すこともできます。

「見つける」は47都道府県・気分・半日／1日・移動半径（1〜200km）・県境をまたぐかを指定できます。固定ルートの選別ではなく、施設候補から条件に応じて訪問順を組み立てます。候補不足時は利用者の半径上限内で段階的に範囲を広げ、1〜2スポットでも提案します。「この条件で乗換つきの経路を作る」は最後に採用したルート、または表示中のルートを引き継いで交通経路を検索します。詳細を開くだけでは交通APIを呼ばず、「運行時刻を確認する」で検索します。

自作の日帰り・宿泊旅程は「この旅程を保存」から保存済みプランへ追加できます。日帰りは順番・滞在時間・固定開始時刻・予算・帰着地・訪問済み記録、宿泊は全日分の行き先・宿泊先・泊数・出発条件を復元します。同じ旅程の重複保存を防ぎ、編集した旅程は別のプランとして保存できます。開き直すだけでは交通APIを呼ばず、古い交通情報は未確認に戻します。

日帰り旅程の「出発前の情報をまとめて調べる」では、先頭3施設の公式案内を確認し、不足する施設だけAIが出典付きで検索します。確認した情報・未確認項目・実行した手順を分けて表示し、途中で取得に失敗しても得られた結果を残します。詳しくは [出発前の施設情報確認](docs/journey-review.md) を参照してください。

編集中の日帰り旅程は、このブラウザのlocalStorageへ自動保存します。再読み込みしても、出発地・日付・順番・滞在時間・固定予定・時間と予算・利用者の費用見積もりを復元します。未反映の入力やプレビュー、取り消し履歴は保存しません。「新しい旅程を作る」で下書きを削除します。保存容量不足などは画面で案内し、復元した過去日の交通情報は無効にして日付変更を促します。「しおりを見る」では現在の予定をテキストで確認・コピーできます。別端末への同期はありません。

編集・制約の再計算はブラウザ内で行い、外部APIを呼びません。料金が不明な項目は0円扱いせず、予算内か未判定と表示します。移動は取得済みの合計時間を区間距離で配分した目安です。行き先・順序・出発条件が変わると古い交通費と移動時間は使わず、徒歩概算へ切り替えます。「交通経路を再検索」で現在のスポットと順序をそのまま `POST /api/routes` の `selected_places` に渡し、交通情報を更新できます。この検索では候補地やAI説明の再生成を行わず、経路が見つからない場合も選んだスポットを勝手に削除しません。

追加候補の検索は `POST /api/search/places` の検索中心に現在の出発地点を指定します。候補検索・交通経路検索は外部APIを使用します。実際の道路、発着時刻、営業時間、料金の保証ではありません。

### API呼び出しの保護

外部APIを呼び出す公開エンドポイントはIP単位で制限します。候補検索は各10回/分、日帰り・ルート検索は各5〜10回/分、宿泊検索は2回/分に加え、対象エンドポイント全体で20回/分の共有上限を適用します。Discoverは30回/分です。上限超過はHTTP 429です。ローカル開発ではメモリストレージを使います。

Cloud Runの複数インスタンス間で制限値を共有するには、自分の環境のRedisを用意し、到達可能な接続URIを`RATE_LIMIT_STORAGE_URI`としてSecret Managerから渡してください。未設定時も起動しますが、制限は各プロセスのメモリ内で管理され、再起動でリセットされます。これは総利用額を制限する仕組みではありません。`get_remote_address`はASGIが認識する接続元IPを使うため、プロキシ配下では信頼できるプロキシだけが転送元IPを設定するようにしてください。任意の`X-Forwarded-For`値を直接信用しないでください。

駅すぱあとAPIは仕様上、アクセスキーを`key`クエリパラメータで送る必要があります。アプリケーションのデバッグログでは値をマスクしますが、プロキシ・APM・HTTPクライアントの詳細ログでもURLクエリを記録しない設定にしてください。Gemini APIキーはURLに含めず、`x-goog-api-key`ヘッダーで送信します。

### ルートのタイムライン

ルート提案APIは出発地、各スポット、帰着地と、その間の移動を `timeline` 配列で時系列順に返します。各スポットの滞在時間は90分として到着時刻を計算します。駅すぱあとAPIは周遊全体の移動時間を返すため、区間ごとの時間は経路上の直線距離比で按分した目安です。実際の区間別発着時刻ではありません。駅すぱあとが返す路線・駅ごとの詳細はタイムライン内の折りたたみ欄に表示します。

フロントエンドは `timeline` がない旧API応答にも対応し、スポットと座標・総移動時間から目安のタイムラインを組み立てます。`start.ps1` はタイムライン非対応のAPIがポート8000で稼働中の場合に、古いサーバーを閉じてから再実行するよう案内します。

通常ルートは最も評価の高い1件だけを返し、日帰り・宿泊プランともにタイムラインで描画します。出発・到着時刻を左軸に示し、スポットカードと移動情報を時系列順に並べます。駅すぱあと経路の詳細は移動行内の折りたたみ欄に表示します。地図には寺社・自然・グルメ・宿泊などのカテゴリ別アイコンと、移動手段別のアイコンを表示します。

### イラストマップ

地図のスポットマーカーは施設名・カテゴリから寺社、自然、グルメ、宿泊、文化・観光、買い物のSVGアイコンを選び、番号バッジ付きで表示します。ルートに含まれる徒歩・電車・バスは、ポリラインの中間に移動手段アイコンとして表示します。線は経路検索の実際の道路・線路形状ではなく、スポット間を示す目安です。ベースマップには淡色のOpenFreeMap Positronスタイルを利用します。

### 気分から作る宿泊プラン

画面で「宿泊あり」と1〜6泊を選び、気分・移動範囲を入力します。`POST /api/itineraries/overnight` は施設検索の結果から宿泊先と観光地を選び、各日で同じ観光地を重複させずに配分します。宿は連泊を前提に1施設を選びます。候補不足時は少ない立ち寄り数で返し、宿が見つからない場合は条件の見直しを案内します。営業時間・空室・宿泊料金・天気は未確認です。

泊数が増えても訪問順の全順列探索を行わず、交通経路検索は1日あたり最大2回、運賃照会は最大1回です。全体で55秒の処理期限を共有し、時間切れの日は交通情報を未確認として返します。画面には待機表示と中止ボタンを用意しています。

## 国土数値情報・旅行データ基盤（フェーズ1）

京都府から始めるローカル試作データベースを `backend/data/travel.sqlite3` に作成します。配布元の使用許諾をデータ版ごとに確認し、公式の京都府P12データを `backend/data/raw/P12-14_26_GML.zip` に置いて取り込みます。ZIPとSQLite DBはGitに含めません。

- `datasets`: データセット名、発行元、取得元URL、版、取得時点、ライセンスと出典表記。
- `places`: 必須の `id`、`name`、`category`、`address`、`latitude`、`longitude`、`description`、原典のレコードID・属性JSON。
- `place_labels`: `atmosphere`、`target_audience`、`activity_type` と信頼度、根拠、生成方法、モデル、プロンプト版。
- `place_embeddings`: 埋め込みモデル、次元、ベクトル、対象テキストのハッシュ。
- `places_fts` と `places_geo`: SQLite FTS5の日本語部分文字列検索とR*Treeによる空間候補検索。意味ベクトル検索の具体的な方式はフェーズ3で決めます。

初期候補データ:

- [国土数値情報 観光資源データ (P12)](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-P12-2014.html): 最新公開仕様は第2.2版、データ基準年は2014年です。点・線・面のデータがあり、今回の検索・ルート提案には京都府の点データ597件のみを使用します。検索用の `category` は `tourism` に正規化し、原典の種別・名称・住所・座標などは `source_attributes_json` に保持します。原典にない説明文は空欄のままです。データは古いため、現存状況や最新情報は保証されません。
- [国土数値情報 宿泊容量メッシュデータ (P09)](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-P09.html): 宿泊施設個別の名前・住所ではなく、宿泊容量のメッシュ情報として扱います。宿泊施設POIの代替にはしません。
- [国土数値情報 バス停留所データ (P11)](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-P11.html): 交通アクセス候補を補う場合に使います。

国土数値情報は、指標・公開版ごとに利用条件が異なります。取り込み前に[データ一覧](https://nlftp.mlit.go.jp/ksj/gml/gml_datalist.html)でその版のライセンスを確認し、[利用ルール](https://nlftp.mlit.go.jp/ksj/other/agreement.html)に沿った出典と加工表記を保存します。`datasets.license_name`、`license_url`、`attribution_text`が埋まらないデータは登録しない方針です。

P12の使用許諾条件は「非商用」で、複製物の再配布は許可されていません。利用規約は、GIS/Excel等のデータベース利用について権利侵害のおそれがある場合に事務局への問い合わせも案内しています。このため取り込んだデータおよび検索結果は現時点ではローカル試作に限定し、公開・再配布はしません。公開サービスに使う場合は、配布元への確認または別途利用許諾が必要です。

京都府P12ポイントデータの取得・登録:

```powershell
cd backend
New-Item -ItemType Directory -Force data\raw | Out-Null
Invoke-WebRequest `
  -Uri "https://nlftp.mlit.go.jp/ksj/gml/data/P12/P12-14/P12-14_26_GML.zip" `
  -OutFile "data\raw\P12-14_26_GML.zip"
python -m app.ingest_p12
python -m app.labeling
```

取込処理は再実行可能で、同じデータセットの既存スポットを置き換えます。SQLiteにはポイント形状のみを登録し、P12の線・面形状はルート候補に使いません。

## ラベル付け（フェーズ2）

初期版は外部LLMを使わず、`backend/app/labeling.py` のキーワードルールで `atmosphere`、`target_audience`、`activity_type` を抽出します。ラベルには一致した原文語句、信頼度、方式 `rule`、ルール版を保存します。明示根拠がない客層などは推測で付与しません。

P12データはローカル検索基盤の試作用として保持し、公開用Dockerイメージには含めません。Docker版は既定の `PLACE_SEARCH_PROVIDER=public_catalog` で起動し、別途生成したOSM候補を検索します。

### Yahoo! JAPAN専用のPOI検索

`backend/.env` の `YAHOO_APP_ID` を使い、自然文・旅程・ルート・候補地一覧を[YOLPローカルサーチAPI](https://developer.yahoo.co.jp/webapi/map/openlocalplatform/v1/localsearch.html)で検索します。登録駅以外の地点は[YOLPジオコーダAPI](https://developer.yahoo.co.jp/webapi/map/openlocalplatform/v1/geocoder.html)で座標を解決します。観光ルートはYahooの寺院・神社・博物館・公園等のジャンルコードを指定し、行政機関名やジャンル外の候補を除外します。同名・約100m以内のYahoo重複候補は1件にまとめます。位置情報または有効なジャンル情報がない候補は使わず、カテゴリ名だけが欠落した場合はジャンルコードから補って警告を付けます。Yahoo APIエラー、結果0件、候補不足時も別の検索エンジンやサンプルPOIには切り替えず、Yahoo結果のみ（該当なしの場合は空結果）を返します。API状態は `GET /api/places/status` で確認できます。

ルート候補は指定された移動半径を上限に、テーマ適合度、出発地点からの近さ、情報量、著名観光地名を使って順位付けします。Yahoo!のライブ施設検索範囲は最大20kmで、候補不足時やそれを超える範囲は同梱OSM候補で補います。同梱候補は全国の全施設を網羅していません。口コミ評価やリアルタイムの訪問者数による順位ではありません。

### Yahoo!候補地の順位同期（第2段階）

第2段階では、明示的に実行する同期コマンドがYahoo!ローカルサーチAPIから候補を取得し、名称と座標が一致するWikidata項目を検索します。見つかった項目のWikipedia記事有無、言語版数、直近30日のページビューと、既存SQLiteのP12照合結果を合成したスコアを`place_popularity`と`place_scores`へ保存します。Yahoo!検索結果にはWikidata IDがないため、完全一致する日本語名と1km以内の座標を使って照合します。照合できないスポットはWikipedia指標なしで記録します。同期は明示実行で、ルート提案は保存済みスコアと著名地スコアを使います。

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.sync_popularity
```

Yahoo! APIキー未設定や検索失敗時は同期を行わず、既存DBデータは削除しません。`TRAVEL_DATABASE_PATH`を設定している場合は、そのSQLiteへ同期結果と候補選定用スコアを保存します。

### オープンデータ統合（第3段階）

既存の`ingest_p12`で取り込んだ国土数値情報P12観光資源データ（京都府）を、Yahoo!候補と名称または座標（約100m以内）で照合します。照合できた候補には公開観光資源データの該当スコアを加えて優先順位を計算します。

この段階で新しいAPIキー、アクセストークン、アカウント登録は必要ありません。使用するのは、既存のローカルSQLiteに登録された国土交通省の公開データだけです。P12の利用条件・出典表示は既存の`datasets`レコードで管理します。観光統計の追加取得や有料APIはまだ使用していません。

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.labeling
```

## 自然文検索（フェーズ3）

`POST /api/search/places` に `{"query":"京都駅周辺で自然を感じられる場所"}` を渡すと、ルールベースで地域、登録済み出発駅、カテゴリー、希望、距離条件を抽出し、Yahoo!ローカルサーチAPIだけでPOIを検索します。位置情報が欠落した候補は除外し、API失敗・結果不足時はYahoo!由来の候補のみ、または空結果を返します。登録駅の「周辺」は1km、徒歩N分は毎分80mの検索半径として扱います。登録駅で解決できない距離指定は警告と空結果にし、別の中心地点へフォールバックしません。

移動時間は駅すぱあとAPIの経路検索で別途評価します。P12ベースのFTS5/R*Tree検索関数はローカルDBの検証用として残しますが、画面・ルート・自然文検索APIのスポット候補取得には使いません。ベクトル検索・意味検索も未導入です。

## 周遊ルート（フェーズ4）

`POST /api/itineraries` は、自然文検索の候補から立ち寄り先を選び、最大3か所の全順列（最大6通り）を駅すぱあとAPIに問い合わせ、最短の公共交通所要時間の順序を採用します。各地点の滞在は一律90分として加算し、既定の18:00帰着期限を超える場合も結果を返し、`feasible: false` と明示します。APIの呼び出し回数を `route_search_calls` に含めます。API契約に応じて検索ごとの利用料が発生し得るため、順列比較を実行するのは利用者がこのエンドポイントを明示的に呼んだ時だけです。

例:

```json
{
  "query": "京都駅周辺で自然を感じられる観光地",
  "departure_station": "京都",
  "departure_date": "2026-10-05",
  "departure_time": "09:00",
  "stop_count": 3
}
```

営業時間、施設での実際の滞在時間、混雑・遅延、地点間の徒歩道順はデータ未整備のため保証対象外です。座標から最寄り駅までのアクセスは駅すぱあとAPIの概算です。

### 交通費の概算

日帰りのルート提案（`/api/routes`）と選択スポットの旅程（`/api/itineraries`）は、採用した立ち寄り順について、駅すぱあと経路探索APIを `searchType=plain` で別途呼び出します。この探索は平均待ち時間方式で、時刻表を使用しません。運賃照会には出発日・時刻を渡しません。全行程を出発地から各スポット経由で出発地へ戻る一つの経路として検索し、運賃と該当する料金の片道合計を `fare_yen` として返します。金額は1人分の周遊全体の概算です。

宿泊プランでは各日について、出発地点・スポット・昼食候補・宿泊施設または帰着駅の順に `searchType=plain` で個別検索します。日ごとの概算を各日の `fare_yen` に、全日分が取得できた場合だけ合計を旅程の `fare_yen` に返します。1日でも取得できない場合、各日で取得できた金額は表示しますが、全体合計は `null` になります。

概算を取得できない場合も旅程自体は返し、`fare_yen` は `null` になります。画面ではその状態を明示します。ダイヤに基づく通常の経路・所要時間とは別の検索結果のため、実際に利用する経路、運賃、特急料金等と異なる場合があります。

## スワイプ提案のオフラインフォールバック

将来の1スポット提案向けに、`IdeaDeck`・`useSwipeDeck` と `GET /api/ideas` のロジックを残しています。「旅をつくる」画面にはスワイプ操作を表示しません。旧アイデアAPIは `backend/data/fallback_dataset.json` を読み込み、最大2件のリアルタイム提案を合計8秒以内で試して不足分を補います。`use_fallback=true` では施設・AI・画像APIを呼びません。現在の「見つける」はこの固定アイデアAPIを使用しません。

### Discoverの動的生成

`POST /api/discover` は `origin`、`area`、`prefecture_name`、`theme`、`course`、`radius_km`、`cross_prefecture`、`variation`、`count` を受け取り、施設単位の候補をその場で組み合わせます。応答は `routes`、`note`、`source` です。登録ルートをそのまま返す方式から切り替えました。通信できない場合もブラウザー側の施設カタログから生成し、取得状況を表示します。

公開カタログモードとYahoo!キー未設定時は同梱施設のみを使います。Yahoo!設定時は最大12秒・1回のライブ施設検索を行い、不足分や20km超の範囲を同梱候補で補います。Discoverでは乗換・AI説明・画像APIを呼びません。候補は有限であり、施設未登録の地域では空結果になります。宿泊施設や未確定の昼食枠を観光地として混ぜません。

### 施設カタログの生成元

既存の `backend/scripts/generate_prefecture_routes.py` と都道府県JSONは施設カタログの生成元として保持します。画面表示ではスポットを重複排除したうえで個別の施設として扱い、登録済みルートの組み合わせや各県5件という件数には依存しません。出典・ライセンスを引き継ぎ、テーマは施設自身の名称・カテゴリから判定します。データ更新・Dockerへの同梱手順は [公開用ランタイム](docs/public-runtime.md) を参照してください。

### 全国の事前サンプル

各提案にはJIS X 0401の2桁都道府県コードと都道府県名を持たせます。`prefecture_code=26` のようにAPIへ渡すと、その都道府県の事前生成データに限定して返します。都道府県を指定した場合は京都府固定のリアルタイム生成を行いません。

Yahoo! Local Searchの `YAHOO_APP_ID` を設定した開発者は、次のスクリプトを手動実行して全国47都道府県それぞれ5件（計235件）の候補データを生成できます。施設情報検索のみを行い、Geminiや画像APIは呼び出しません。必要件数や近接した施設の組み合わせが揃わない場合、既存のデータセットを置き換えずに失敗します。Yahoo!へのAPI通信を行うため、実行前に利用条件・上限を確認してください。

```powershell
cd kyoto-route-planner\backend
.\.venv\Scripts\python.exe scripts\generate_national_fallback_dataset.py
```

生成後、バックエンドを再起動するとデータセットが読み込まれます。

```powershell
cd kyoto-route-planner\backend
# APIキーを設定したうえで、開発者が必要なときに手動実行します。
.\.venv\Scripts\python.exe scripts\generate_fallback_dataset.py --count 30
```

生成スクリプトはYahoo!からスポット情報、Wikimedia Commons から商用利用可能な画像とクレジット、Geminiから説明文を取得し、検証後にJSONを置き換えます。必要な件数を取得できない場合は既存データを維持します。画像APIやGeminiのキーが未設定・利用不能の場合も、画像なし・定型説明のカードを生成できます。ファイルを更新した後はバックエンドを再起動してください。

## ローカル起動

Python 3.12以降とNode.js 24以降が必要です。

初回のみ、`backend/.env.example` を `backend/.env` にコピーして `EKISPERT_API_KEY` と `YAHOO_APP_ID` を設定し、依存関係を準備します。Yahoo! APIキーが未設定の場合、POI検索は空結果を返します。

```powershell
cd kyoto-route-planner\backend
Copy-Item .env.example .env
# .envを開き、取得済みのキーを EKISPERT_API_KEY= と YAHOO_APP_ID= に設定します。
# 例として、ローカル開発では EKISPERT_APPLICATION_URL=http://127.0.0.1:8000 を使います。
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

```powershell
cd ..\frontend
npm ci
npm run build
```

`start.bat` はフロントエンドのソースがビルド済みファイルより新しい場合、自動で `npm run build` を実行してからAPIとブラウザーを起動します。Windowsの既定文字コードに依存せずUTF-8の`.env`を読めるよう、バックエンドはPython UTF-8モードで起動します。Git pull後に以前のAPIサーバーがポート8000で動き続けている場合は、古いコードを誤って使わないよう起動を停止します。その場合は以前のAPIウィンドウを閉じてから`start.bat`を再実行してください。起動したAPIウィンドウを閉じるとアプリが停止します。

```powershell
cd ..
.\start.bat
```

「最寄り駅を特定できませんでした」が出続ける場合は、Git pull前の古いAPIサーバーがポート8000で動いていて `/api/origins/nearest` が404になっている可能性があります。古いサーバーを終了して再起動してください。手動で起動する場合は `$env:PYTHONUTF8='1'` を設定してから `.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000` を実行します（未設定だと `.env` の読み込みで起動に失敗します）。

駅すぱあとAPIの利用登録ドメインに開発用ドメインを登録してください。ローカル開発では `127.0.0.1` のような実際の利用URLを `EKISPERT_APPLICATION_URL` に設定し、`localhost` だけに寄せすぎないことが重要です。登録ドメインとローカル開発の利用条件は必要に応じて駅すぱあとAPIの窓口に確認してください。

## Google Cloud Runへの公開

Cloud Run、Cloud Build、Artifact Registryを有効にしたGoogle Cloudプロジェクトと、`gcloud` CLIが必要です。Google Cloudの利用料は駅すぱあとAPI・地図タイルの利用条件とは別です。無料枠の対象・料金はプロジェクトごとに確認してください。

このアプリのフォルダー (`kyoto-route-planner`) でコマンドを実行してください。APIキーやRedis接続URIは自分のGoogle CloudプロジェクトのSecret Managerに登録し、ソースコードやブラウザー環境変数に記載しないでください。Docker版の施設検索にYahoo!キーは不要です。以下は公共交通経路とルート紹介文を有効にする設定例です。口コミ要約は別途 [公開用ランタイム](docs/public-runtime.md) の設定が必要です。

```bash
gcloud secrets create gemini-api-key --project YOUR_OWN_PROJECT_ID --data-file=PATH_TO_PRIVATE_KEY_FILE
```

`YOUR_OWN_PROJECT_ID` は自分のプロジェクトIDに、`PATH_TO_PRIVATE_KEY_FILE` はキーだけを記載したGit管理外のファイルに置き換えてください。Google Cloud Consoleから登録することもできます。公共交通経路を使う場合は `ekispert-api-key` も登録してください。Cloud Runの実行サービスアカウントには、参照する各シークレットに対する `Secret Manager Secret Accessor` (`roles/secretmanager.secretAccessor`) 権限が必要です。

```bash
gcloud secrets add-iam-policy-binding gemini-api-key \
  --project YOUR_OWN_PROJECT_ID \
  --member="serviceAccount:YOUR_CLOUD_RUN_SERVICE_ACCOUNT" \
  --role="roles/secretmanager.secretAccessor"
```

`YOUR_CLOUD_RUN_SERVICE_ACCOUNT` はCloud Runサービスの実行サービスアカウントに置き換え、ほかのシークレットにも同じ権限を付与してください。

```powershell
gcloud run deploy conciergo-demo `
  --project YOUR_OWN_PROJECT_ID `
  --source . `
  --region asia-northeast1 `
  --allow-unauthenticated `
  --set-secrets "EKISPERT_API_KEY=ekispert-api-key:latest,GEMINI_API_KEY=gemini-api-key:latest" `
  --set-env-vars "PLACE_SEARCH_PROVIDER=public_catalog,EKISPERT_APPLICATION_URL=https://your-registered-domain.example"
```

上記コマンドは自分の環境へ公開する段階で実行する例です。使用するシークレットを先に作成し、Cloud Run実行サービスアカウントに参照権限を付与してください。Gemini未設定時はテンプレート文が使われます。複数インスタンスでレート制限を共有する場合は、自分のRedisのURIを `RATE_LIMIT_STORAGE_URI` に追加します。`your-registered-domain.example` は、駅すぱあとAPIに登録した実際のアプリドメインに置き換えてください。Cloud RunのURLまたは独自ドメインが駅すぱあとAPIの登録条件に合うか、公開前に提供元へ確認してください。

## 動作・制約

- 交通経路の検索・運賃照会は駅すぱあとAPIを使います。宿泊プランは日数に比例した回数に制限します。APIキーの契約に応じて利用料が発生する可能性があります。
- 電車・バス等の公共交通ルートと時刻は駅すぱあとAPIの応答に基づきます。駅すぱあとAPIが利用できない場合、成功したように見せず画面にエラーを表示します。
- 行き先の選定と訪問順は、指定半径内の施設候補と直線距離による近接性に基づく提案です。全観光地を網羅したり、営業状況・滞在時間・最適な観光順を保証したりするものではありません。
- 出発駅は駅すぱあとAPIの駅名で経路探索し、途中の観光地点は座標で渡します。地点から駅までの所要時間は直線距離と毎分80mによる概算で、歩道に沿った実際の徒歩道順ではありません。
- 地図は候補地・出発地・帰着地と、地点間をつなぐ目安の線を表示します。実際の道路・線路形状ではありません。「全体を見る」で表示範囲を戻せます。地図が読み込めなくても旅程の一覧は利用できます。
- OpenFreeMapおよびOpenStreetMapへの帰属表示を画面に含めています。
